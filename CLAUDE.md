# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single Helm chart (`charts/capi-kamaji-vsphere`) that renders the Cluster API objects for one Kamaji tenant cluster whose worker nodes are vSphere VMs. There is no Go code: the repo is only templates, values and docs. The chart runs against a **management cluster** that already has Kamaji, CAPI, CAPV (vSphere provider) and, optionally, the CAPI in-cluster IPAM provider installed. One Helm release equals one tenant cluster.

## Commands

```bash
# Lint (this is the only CI check; CI pins Helm v3.3.4)
helm lint ./charts/capi-kamaji-vsphere

# Render everything / a single template to inspect output
helm template test ./charts/capi-kamaji-vsphere
helm template test ./charts/capi-kamaji-vsphere -s templates/machine-deployment.yaml
helm template test ./charts/capi-kamaji-vsphere -f my-values.yaml --set cluster.metrics.enabled=true
```

There are no unit tests (no helm-unittest). To check a change, render it with `helm template` and read the output.

`charts/capi-kamaji-vsphere/README.md` is generated by **helm-docs** from the `# --` comments in `values.yaml`. When you add or change a value, give it a `# --` comment and regenerate the README with `helm-docs`, or edit the values table by hand to match (helm-docs isn't always installed locally).

## Release process

1. Bump `version` in `Chart.yaml`, and the version badge in the chart README to match.
2. Push a `v*` tag. `.github/workflows/release.yml` packages the chart and publishes it to the `gh-pages` branch of `clastix/charts` (served at https://clastix.github.io/charts).

## Architecture

### Resource graph (per release)

- `Cluster` → `controlPlaneRef: KamajiControlPlane` + `infrastructureRef: VSphereCluster`. All three share the cluster name.
- `KamajiControlPlane` (`controlplane.cluster.x-k8s.io/v1alpha1`): the hosted control plane runs as pods on the management cluster. The `cluster.controlPlane.*` values map onto it almost one to one.
- For each entry in `nodePools`: a `MachineDeployment` (`<cluster>-<pool>-md`) that references a hash-suffixed `KubeadmConfigTemplate` and a hash-suffixed `VSphereMachineTemplate`.
- `InClusterIPPool` (when `ipamProvider.enabled`): one pool named after the cluster. Node pools use it through `addressesFromPools.enabled`.
- `cpi-manifests.yaml`: the vSphere Cloud Controller Manager runs **on the management cluster** in the release namespace, not inside the tenant. It reaches the tenant API through the Kamaji-generated `<cluster>-admin-kubeconfig` secret (key `admin.svc`) and reads vCenter credentials from `vSphereCloudControllerManager.secret.name`. This split keeps vSphere credentials away from tenants.
- `metrics.yaml` (when `cluster.metrics.enabled`): a Service plus a ServiceMonitor that scrape the control-plane pods, with RBAC so Prometheus can read the `<cluster>-api-server-kubelet-client-certificate` secret.

The cluster name is `cluster.name`, or the release name when that is unset (helper `cluster-api-kamaji-vsphere.cluster-name`). Every object carries the `cluster.x-k8s.io/cluster-name` label. Keep that label on any new resource.

### Rolling updates via content-hashed templates

CAPI machine templates are immutable, so node changes roll out by creating new template objects:

- The template spec bodies live in named helpers: `kubeadmConfigTemplateSpec` (`_kubeadm-config-template.tpl`) and `vSphereMachineTemplateSpec` (`_vsphere-machine-template.tpl`).
- `kubeadmConfigTemplateHash` and `vSphereMachineTemplateHash` render the same helper and take the first 8 characters of its sha256. That hash becomes the suffix of the object name.
- `machine-deployment.yaml` computes the same hash to build its `configRef` and `infrastructureRef` names. When the spec changes, `helm upgrade` creates a new template and repoints the MachineDeployment, and CAPI then replaces the machines.

Rules that follow from this:
- Any field that should trigger a node rollout has to be rendered inside the spec helper. Anything outside the helper doesn't change the hash.
- The context dict passed to a helper must be identical in the template file and in `machine-deployment.yaml`, or the names won't match. The kubeadm helper takes `(dict "nodePool" .)` and the vSphere helper takes `(dict "nodePool" . "Global" $)`. Inside the vSphere helper, root values are reached through `.Global.Values`.

### Template conventions and gotchas

- cloud-init/Jinja placeholders inside templates must be escaped so Helm leaves them alone: ``"{{`{{ ds.meta_data.local_ipv4 }}`}}"``. Strings that come from `values.yaml` (such as the `preKubeadmCommands` defaults) are not passed through `tpl`, so they stay unescaped there.
- Kamaji addons (`cluster.controlPlane.addons.{coreDNS,kubeProxy,konnectivity}`) are emitted with a `hasKey` check. Setting an addon to `null` in user values removes the key, which disables that addon. `{}` enables it with defaults.
- Workers join with `cloud-provider: external`, and the controller-manager defaults include `--cloud-provider=external`. Nodes stay tainted until the CPI initialises them, so a stuck taint usually means the CPI has a vSphere credentials problem.
- When a node pool has `autoscaling.enabled`, its `MachineDeployment` is rendered without `replicas`, on purpose. If `replicas` were rendered, Helm would compete with the autoscaler for the field. Helm 4 upgrades would fail with a server-side apply conflict on `.spec.replicas`, or reset the count with `--force-conflicts`. Helm 3 would overwrite the count whenever the `replicas` value changed. Cluster API defaults the field from the min/max-size annotations instead. The same pools also get `capacity.cluster-autoscaler.kubernetes.io/*` annotations, which enable scale from zero. These are built from `numCPUs`, `memoryMiB`, `diskGiB`, `labels` and `taints`, so they follow those values automatically. Whitespace is stripped from labels and taints because the autoscaler's parser doesn't trim and silently drops a malformed taint.
- `vSphere.identityRef.type` is either `VSphereClusterIdentity` (the default; a cluster-scoped identity that several clusters can share) or `Secret`.
- On `helm uninstall`, deleting the `InClusterIPPool` can fail while machines still hold addresses from it. The README's troubleshooting section describes the workaround.
